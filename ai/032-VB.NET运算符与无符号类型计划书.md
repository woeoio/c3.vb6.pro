## 1. 新增的语法

| 类别 | 语法 | 落脚点 |
|---|---|---|
| 移位 | `a << n` / `a >> n` | 词法 `Shl/Shr` → `BinaryOp::Shl/Shr` → RTL `vb6_Shl/Shr/ShrU` |
| 复合赋值 | `+= -= *= /= \= ^= &= <<= >>= Mod=` | 词法 10 个独立 token → **解析期脱糖**成 `target = target op value` |
| 引用比较 | `a IsNot b` | 解析期脱糖成 `Not (a Is b)` |
| 三元 | `If(cond, a, b)` | 解析期产 `IndexOrCallExpr("If")` → 发**裸 C 三目**（真短路） |
| 类型 | `SByte` / `UInteger` / `ULong` / `ULongLong` | `Vb6Type::SByte/UInteger/ULong(既有)/ULongLong` |
| 转换函数 | `CSByte` / `CUInt` / `CULng` / `CULngLng` | `builtin_funcs.inc` 登记 + RTL `vb6_CSByte/CUInt/CULng/CULngLng` |

### 1.1 位宽口径：阶梯对齐 8/16/32/64

`U<x>` 恒等于「`<x>` 的无符号版」，与既有 `Vb6Type::ULong = 19 → uint32_t` 完全吻合：

| VB 类型 | C 类型 | 位宽 | 对照 |
|---|---|---|---|
| `SByte` | `int8_t` | 8 | — |
| `UInteger` | `uint16_t` | 16 | `Integer` = 16 位（C3 沿用 VB6 口径） |
| `ULong` | `uint32_t` | 32 | `Long` = 32 位 |
| `ULongLong` | `uint64_t` | 64 | `LongLong` = 64 位 |

`ULong` 枚举值**早已存在**（`mapType`→`uint32_t`、`typeSize`→4、typelib→`VT_UI4`），
但词法器没有 `ulong` 关键字、也不在 `isIntegral` 里 —— 属"半截活"，本次补齐。

### 1.2 绑定力（插入 `bpTable_` 的推导，不是拍脑袋）

VB6 既有优先级：`Or(2,3) < Xor(3,4) < And(4,5) < Eqv/Imp(6,7) < 比较(8,9) < &(10,11)
< 加减(12,13) < Mod(14,15) < \(16,17) < 乘除(18,19) < ^(21,20) < Like/Is(22,23)`

- `Shl/Shr = (9,10)` —— 夹在比较(8) 与 `&`(10) 之间。两侧夹逼：`1 << 2 + 3` 必须是 32
  （算术高于移位）而 `1 << 1 = 2` 为真（移位高于比较）。
- `IsNot = (22,23)` —— 与 `Is` 完全一致（它就是 `Is` 的否定形）。
- 10 个复合赋值 token **不登记任何绑定力** —— Pratt 中缀循环拿到 `{0,0}` 自然停住，
  再在语句层收编。

### 1.3 三处必须小心的既有冲突

1. **`&` 后缀 vs `&=`**：`lexer.cpp` 的 `scanIdentifierOrKeyword` 里，`&` 后跟非字母
   数字（含 `=`）就被并进标识符 —— 所以 `x& = 5` 的 `&` **到不了**运算符分支，而
   `x &= 5`（带空白）走 `scanOperator`。两者天然不冲突，已用对照用例 C7 钉住。
2. **`<<`/`>>` vs `<`/`<=`/`<>`**：`<` 分支先 `match('<')`（再判 `=`）出 `Shl/ShlEq`，
   之后才判 `<>`/`<=`/`<`；`>` 分支对称。对照用例 C5 钉住 `<` 家族。
3. **`Mod=` 不做空白容忍**：`x Mod= 2` 之间的 `Mod=` 必须紧贴。刻意不容忍
   `x Mod = 2`，因为与 `If x Mod 2 = 0` 形状太近，误吞的代价远大于省一次空格。

## 2. 五处"做法"上的取舍（都是刻意的）

### 2.1 复合赋值：解析期脱糖，而不是新增赋值节点

`parseLabelOrAssignmentOrCall` / `parseLetStmt` 在 `if (match(TokenKind::Equals))`
**之前**拦一道复合赋值，用 `ASTCloner` 深拷左值，产出
`AssignmentStmt(loc, target, BinaryExpr(op, clone(target), value))`。

- 收益：语义层/发码层**零改动**；`arr(i) += 7`、`udt.a += 41` 自动可走。
  已用探针 A9/A10 验证。
- 代价：左值被求值两次（VB.NET 里是"求值一次、写回一次"）。对 `arr(i) += 1` 这类
  常见形状（下标是无副作用表达式）无差异；对有副作用的左值（如 `f() += 1`）会差异。
  **记为本扩展的已知语义近似**。
- `&=` 映射到 `BinaryOp::Concat`，**不是** `Add` —— 字符串连接语义。
- **`Set` 不收复合赋值**（`parseSetStmt` 刻意不接）：Set 是对象引用赋值，
  VB.NET 里同样非法。

### 2.2 `IsNot`：解析期脱糖成 `Not (a Is b)`

理由：`exprYieldsVbBoolean` 认 `BinaryOp::Is` 为布尔，于是 `Not` 走**逻辑**取反，
拿到正确的布尔语义，下游（`CStr`/`And`/装箱）零改动。
不能用 `<>` 顶替 —— `Is` 是**引用**比较，`=`/`<>` 是**值**比较。

### 2.3 `If(c,t,f)`：发裸 C 三目，类型自算

- 短路是真的（C `?:`），探针 `if_short_circuit`（`If(d<>0, 100/d, 42)` 在 d=0 时得 42）
  就是对 IIf 急切求值的对照判据（IIf 那条报 ERROR11）。**副产品**：`If` 比 `IIf` 更安全。
- `addBuiltinFunc("If", Variant)` 只是让语义层知道"这个名字存在"，**真结果类型由
  `inferExprType` 自算**（同型取该型 / 都数值取 promote / 任一支 String 取 String /
  否则 Variant）。两处口径必须一致，所以 `isPolymorphicBuiltin` 的 denylist
  （`iif/choose/switch`）也必须加上 `"if"` —— 否则 `CStr(If(...))` 会走
  `vb6_CStr(vb6_VariantFromValue(<BSTR>))` → C2440。
- **已知不支持形状**：C 没有"序号化三目"，`If(True, f(), 0)` 可能同时调用 `f()`。
  VB6 常见用法（下标表达式、除法保护）不受影响，约定为病态形状不支持。

### 2.4 移位：不直接发 C 的 `<< >>`，改发 RTL inline

C 的移位在三处与 VB.NET 语义不同，其中两处是 **UB**：

1. **计数屏蔽**：VB.NET 把计数屏蔽到操作数位宽内；C 对"计数 ≥ 位宽"是 UB。
   `vb6_Shl/Shr/ShrU` 统一按 **63** 取模（取 63 而不是按左操作数位宽，见第 3 条）。
2. **有符号左移溢出**（`&H80000000 << 1`）在 C 里是 UB。按 `uint64_t` 位模式左移，
   位模式确定，再由 cgen 截断回目标类型 —— 结果与 VB.NET 的 wrap 一致。
3. **结果类型抬到至少 32 位**：VB.NET 的 `Integer` 是 32 位，C3 的 `Integer` 是 16 位。
   照搬会让 `1 << 20` 被截成 0。所以窄整型（SByte/Byte/UInteger/Integer/Boolean/Long）
   一律抬到 `int32_t`，`ULong→uint32_t`、`LongLong→int64_t`、`ULongLong→uint64_t`、
   `LongPtr→intptr_t`。这也是"计数按 63 取模"的原因。
4. **右移的有符号性**：VB.NET 对有符号整型是**算术**右移，对无符号整型
   （Byte/UInteger/ULong/ULongLong）是**逻辑**右移。C 对有符号数是实现定义，
   所以分成 `vb6_Shr` / `vb6_ShrU` 两支，由 cgen 按左操作数的有符号性选。

### 2.5 新类型：不新造 `VT_UI1/UI2/UI4`，Variant 装箱复用既有最小 VT

| 类型 | 装箱 | 理由 |
|---|---|---|
| `SByte` | `VT_I2`（int16_t 承载） | 能无损装下 |
| `UInteger` | `VT_I4`（int32_t 承载） | 能无损装下 |
| `ULong` | 既有路径（`VT_I4`…） | 枚举早已存在 |
| `ULongLong` | `VT_I8`（int64_t 承载） | 能无损装下（> 2^63 例外） |

代价：`VarType()` 对这些值答**有符号档**。收益：值不丢 + 全部走既有已测分支 +
RTL 装箱路径一行不改。

## 3. 一等类型化的关键：`knownNarrowIntVars_`

**根因**：`symTab_` 只有模块作用域，**局部变量/形参/返回槽在它里面不可达**。
这四档的 C 型（`int8_t/uint16_t/uint32_t/uint64_t`）又都不在既有的
`int32_t | int16_t | VBABOOL` 那一支里，于是 `inferExprType` 一律答 Variant。
后果（实测）：

- `CStr(u)`（u As ULong）→ `vb6_CStr(vb6_VariantFromValue(u))` →
  `_Generic` 的 `unsigned int: vb6_VariantLong` 把 `&HFFFFFFFF` 打成 **-1**；
- `Debug.Print u` → `vb6_DebugWriteLong((int32_t)(u))` → 同样 **-1**。

**做法**：新增一张 `name → Vb6Type` 的表 `knownNarrowIntVars_`（仿 `knownByteVars_` /
`knownBoolVars_` / `knownIntVars_` 的并存登记口径），在
局部 `Dim`/局部 `Const`/形参/返回槽 四处登记；消费点在 `inferExprType` /
`isDefinitelyVariantExpr` / CStr 分派 / Debug.Print 分派。
**类型映射只写一份**：`CCodeGen::isNarrowIntVbType` + `narrowIntTypeOfCType`
（`cgen_util_type.cpp`），登记点与消费点都调它 —— 免得"同一个决定抄两遍"
（本仓反复量到的那一族）。

模块级变量**不进**这张表：它们在 `symTab_` 里可达，且本表随过程入口 `clear()`。
CStr 分派另留一条 `inferExprType` 兜底，覆盖模块级/表达式两种落点。

> **rev2 补记**：`LongLong`（`int64_t`）的**局部**后来也归进了这张表 —— 它原先谁也没
> 登记（`int64_t` 不在任何一支），`Dim x As LongLong` 在 `inferExprType` 里同样隐身为
> Variant，`CStr(u64 + x)` 这类混算于是走 Variant 装箱、撞上 `unsigned long long:
> vb6_VariantLong` 那个有符号兜底（实测打成 -1）。详见 3.4 的"顺带挖出的既有盲区"。
> 它不算"新四档"，只是**借这张表把类型做可见**；`isNarrowIntVbType` /
> `narrowIntTypeOfCType` 的集合没动（那四档的判据保持原样）。

### 3.1 无符号输出：`vb6_CStrULong` / `vb6_CStrULongLong`

不复用 `vb6_CStrLong/LongLong`：那两条是有符号口径（`%d`/`%lld`），2^31 以上打成负数。
与 Fix 084m 另开 `vb6_CStrLongLong` 同一处理由（`vb6_Format` 不认 VT_I8）。
`SByte`/`UInteger` 的值域 ⊆ `int32_t`，有符号与无符号十进制**同字面**（`-128`/`65535`），
故仍复用 `vb6_CStrLong`。

### 3.2 `\` 与 `Mod`：四档 helper，判据只有一处

`vb6_IntDiv` / `vb6_Num_Mod` 的形参都是 `int32_t`，无符号操作数会先被按有符号解释 ——
实测 `&H80000000 As ULong \ 2` 得 **3221225472**（应为 1073741824），
因为 `(int32_t)&H80000000 = -2147483648`。故新增六条 helper：

| 结果档 | `\` | `Mod` |
|---|---|---|
| `Long`（32 有符号） | `vb6_IntDiv(int32,int32)` | `vb6_Num_Mod(int32,int32)` |
| `LongLong`（64 有符号） | `vb6_IntDivLongLong` | `vb6_Num_ModLongLong` |
| `ULong`（32 无符号） | `vb6_IntDivULong` | `vb6_Num_ModULong` |
| `ULongLong`（64 无符号） | `vb6_IntDivULongLong` | `vb6_Num_ModULongLong` |

除零一律错误 11。**档位与结果类型只由 `CCodeGen::intDivResultType(lt, rt)` 一处给出**：
它先取 §3.4 的提升结果，再把窄档统一落 `Long`（VB 的 `\` 表：两个窄整型的商仍是
更宽的有符号型）。`inferExprType` 与 `cgen_expr_binary.cpp` 都调它 —— 这是本仓反复
量到的"同一个决定抄了两遍"那一族（#234 拿 DC / #235 画笔色 / #247 几何宿主路）里
最容易踩的一处：改前 cgen 自带一套"任一侧 ULong/ULongLong 就发无符号版"，而
`inferExprType` 另写一套，`2 \ u` 这类换边写法就会漂移。

`vb6_IntDivLongLong` / `vb6_Num_ModLongLong` 是**为了补全档位**才加的：32 位异符号
（`ULong \ Long`）按 §3.4 要升到 64 位**有符号**再除，而 `vb6_IntDiv` 只有 `int32_t`
形参，缺这两条就只能退回 32 位截断（实测旧值 `4294967295 \ -2` 得 1，修正后
**-2147483647** —— 与 VB.NET 的 `UInteger \ Integer = Long(64)` 同值）。

### 3.3 位运算 `& | ^ Eqv Imp`：按档收口，不再一律 `(int32_t)`

原路径把两侧硬转 `(int32_t)`。实测 `u3 = (1 << 40) Or 255` 得 **255** ——
`(int32_t)(2^40) = 0`，高 32 位整段丢掉。改为：任一侧 `ULongLong` → `uint64_t`；
否则任一侧 `ULong` → `uint32_t`；否则保持既有的 LongPtr 字面量→`intptr_t`、
其余→`int32_t`（Fix 082 口径不动）。

### 3.4 整型之间的提升：VB.NET 的三条策略，**不是** C 的"无符号优先"

> 本节是收到用户反馈后重写的（原版把异符号混算写成"等宽即最高位宽胜出"，是错的）。

**权威口径**：MSDN *Data Types of Operator Results* 的 Integer Arithmetic 三条策略：

1. 两侧同型 → 结果就是该型（例外：`Boolean` 强制升 `Short`）；
2. **无符号与有符号混算 → 结果取有符号型，且范围至少不窄于两者中任一**；
3. 其余情况 → 通常取两者中较大的那个型。

注意第 2 条并**不是**"取有符号"或"取无符号"这种二选一，也不是 C/C++ 那条
"无符号优先"—— 它要求的是**能容纳两者取值范围的有符号型**。按位宽映射到 C3 的阶梯，
就是下面这四条（C3 的 `Integer`/`Long`/`LongLong` 是 16/32/64 位，正好比 VB.NET 的
`Short`/`Integer`/`Long` 各低一阶，所以规则要按**位宽**套，不能按名字套）：

| 情形 | 规则 | 例（C3 记法） | 结果 |
|---|---|---|---|
| ① 同符号 | 取更宽的那个 | `ULong ⊕ UInteger` | `ULong` |
| ② 异符号，有符号侧更宽 | 取有符号侧（它完整容纳无符号侧） | `LongLong ⊕ ULong` / `Long ⊕ UInteger` | `LongLong` / `Long` |
| ③ 异符号，无符号侧不窄于有符号侧 | 取**比无符号侧再宽一档的有符号型** | `Byte ⊕ SByte` / `UInteger ⊕ Integer` / `ULong ⊕ Long` | `Integer` / `Long` / `LongLong` |
| ④ 无符号侧已是 64 位 | 没有更宽的有符号整型 → VB.NET 是 **Decimal** | `ULongLong ⊕ Long(L)` | C3 取 `ULongLong`（见下） |

**为什么不能用"rank 大者胜"**（原来的做法）：rank 只按**位宽**排，于是
`Integer + UInteger`（等宽异符号）会取到 `Integer`，而 `Integer` 装不下
`UInteger` 的全部取值 —— VB.NET 的答案是更宽的有符号型。C 的方向也同样是错的，
只是错法不同：C 对同宽异符号取**无符号**（`uint32_t + int32_t → uint32_t`），
负的有符号侧会被当成大正数。**这一处不是"类型被问错"，是值真会错。**

**④ 那一格的取舍**（C3 与 VB.NET 唯一的差异）：VB.NET 给 Decimal。C3 没有 Decimal
算术（`Vb6Type::Decimal` 在 `mapType` 里兜底成 `vb6_VARIANT`，RTL 只有 `vb6_CDec`
装箱，没有一条 Decimal 的加/减/乘/除），所以取 `ULongLong`。理由与边界：

- `+ - *` 在补码下**有符号与无符号的位模式完全相同**，取 `ULongLong` 只影响"按哪种
  符号印出来"——而无符号打印正是真值（`2^32 - 1` 而不是 `-1`）；
- `\ Mod` 也取 `ULongLong`：与 `+ - *` 同一口径，且给出数学上正确的商/余；
- 与 VB.NET 不同只出现在"有符号侧为负"或"结果 ≥ 2^64"这类 VB.NET 本身会抛
  OverflowException / 需要 Decimal 的角落。

**另外两处与 VB.NET 的差异**（都记在 §6 已知边界里）：`Boolean` 不参与这张表
（VB.NET 里它参与算术时被强制升 `Short`，C3 保留了 VB6 的老口径）；`LongPtr` 也不
参与（宽度目标相关，`TypeSystem` 拿不到目标架构）。

#### 发码层：`promote` 答对了还不够，C 会自己算成另一个值

`promote` 只是**结果类型**的口径。`+ - *` 与关系比较在 C 里是裸发运算符的
（`(a + b)` / `(a > b)`），而 C 自己的通常算术转换方向与上面第 2 条相反。
所以 `mixedSignWidenCType()`（`cgen_expr_binary.cpp` 文件局部）在收口前插一次显式
加宽，**只在"提升结果严格宽于两个操作数"那一档插** —— 这一档恰好是 C 会算错的那一档：

- 同符号：C 也取更宽的那个，方向一致，不插；
- 包含关系（如 `LongLong + ULong`）：C 会把 `uint32_t` 提到 `int64_t`，已经对了，不插；
- 64 位异符号：C 给的也是 `uint64_t`，与 `promote` 的 `ULongLong` 一致，不插。

后两条同时保证了**存量语料零影响**：既有类型里唯一的异符号组合是 `Byte` 对
`Integer`/`Long`/`LongLong`（都是有符号侧更宽 = 包含关系），一条都不落进要插转换的那档，
所以既有语料的发射形状（以及 emit-manifest 的哈希）不变。

**负控实测**（把 `promote` 退回"rank 取大者"的旧口径，编 `tests/test_vbnet_ext.bas`，
双架构同值）：

| 表达式 | 坏版（C 方向 / 旧 rank） | 修后 | 说明 |
|---|---|---|---|
| `CStr(u32 + 1)`（`ULong`=4294967295） | `0` | `4294967296` | C 在 uint32 处回绕 |
| `CStr(1 + u32)` | `0` | `4294967296` | 旧 rank 还会**看谁在左**（等宽取左值） |
| `If u32 > -1` | `F` | `T` | C 把 `-1` 转成 uint32 再比 |
| `If -1 < u32` | `F` | `T` | 同上，换边也一样错 |
| `CStr(u32 \ -2)` | `1` | `-2147483647` | 旧实现把除数也按 uint32 收口 |
| `CStr(u32 Mod -3)` | `2` | `0` | 同上（VB.NET 的 `Long(64)` 域答 0） |

六条全部只在"退旧口径"时变红，是本次新规则的**反向判据**；`VE-mix-u64-*` 与
`VE-mix-byte-plus-sbyte` / `VE-mix-uint-plus-int` 是各档的**锁定值**（拦另一个方向：
把提升结果收窄回去）。

#### 顺带挖出的既有盲区：`Dim x As LongLong` 的局部看不见

写 ④ 那一格的断言时实测 `CStr(u64 + i64)` 得 **-1**（应 4294967295）、
`u64 - i64` 得 **1**。根因不在提升规则：`int64_t` 的局部变量**不在任何 known 表里**
（新四档有 `knownNarrowIntVars_`，`LongLong` 没有）→ `inferExprType(i64)` 答 Variant
→ 混算结果被问成 Variant → 走 `vb6_CStr(vb6_VariantFromValue((u64 + i64)))`，
而 `_Generic` 表里 **`unsigned long long:` 关联的是 `vb6_VariantLong`（int32 形参）**，
uint64 被截成 int32。修法是把这个盲区补上（局部与局部 `Const` 两处登记
`int64_t → LongLong`，并在 `CStr` / `Debug.Print` 两条消费链补 `LongLong` 档）。
`_Generic` 的那个有符号兜底**没动**（改它要连带 VT_UI8 的全部读取侧），
留作已知边界。

#### 老发现的坑：`promote` 取"位宽更大"会把 64 位整型排到浮点之上

补档时顺手把 `LongLong`/`ULongLong` 也按位宽排到 6 档（与 Currency 同档），
结果是 `Single(4)/Double(5)` 被压过。后果不是算术算错（`+` 直接发裸 C，
C 自己会把 `int64 + double` 提成 double），而是**结果类型被问错**：上层 `CStr` 按
`inferExprType` 选入口，一旦答整型就发 `vb6_CStrLongLong/…`，把 `5.5` 打成 `5`。

修法两处，缺一不可：

1. **`promote` 里加"浮点/货币/Decimal 侧必胜，与位宽无关"**，在整型规则之前返回。
   对改动前的类型表这是**恒等变换**（浮点/货币档本来就高于所有整型档），既有行为零变化。
2. **`LongPtr` 刻意不进任何一张表**。它的宽度是**目标相关**的（x86 4 / x64 8），而
   `TypeSystem` 这一层**拿不到目标架构**（只有后端的 `targetArch_`，且
   `typeSize(LongPtr)` 本身也还在用宿主 `sizeof(void*)`，既有隐患 Fix 081e）。
   写死任何一档都会错：写 6 之后 `LongPtr + Double` 被判成 LongPtr，
   `CStr(p + 1.5)` 出 4（x86 与 x64 **都是** 4，因为档位是宿主侧算的）；
   写 3 又会在 x64 上低估。正确修法要先把架构信息贯通到语义层，不在本次范围。
   （C3.exe 自身是 **x64 宿主**，所以 `sizeof(void*)` 在编译器里恒为 8，
   想用宿主宽度推目标宽度行不通 —— 这正是最初写错的原因。）

**负控实测**（把 LongLong/ULongLong/LongPtr 一律登记 6 档、并去掉上面第 1 条，
编 `tests/test_vbnet_ext.bas`）：

| 表达式 | 坏版 | 修后 | 说明 |
|---|---|---|---|
| `CStr(u3 + 1.5)`（ULongLong） | `5` | `5.5` | `vb6_CStrULongLong` 截断 |
| `CStr(u3 + CCur(1.5))` | `5` | `5.5` | Currency 侧同样被吞 |
| `CStr(p + 1.5)`（LongPtr） | `4` | `4.5` | 登记 6 档所致 |
| `CStr(p * 2.5)` | `7` | `7.5` | 同上 |
| `CStr(ll + 1.5)`（LongLong） | `5.5` | `5.5` | **没**截断：LongLong 在 CStr 那侧没有整型分支，走 Variant 路 |

最后一行正是"为什么判据必须落在真算出来的值上"：同一个 rank 错误，会不会真丢值
取决于下游发码有没有对应分支。**"语法通过 ≠ 取值正确"，也不能靠读代码判断有没有丢值。**

#### 移位的结果类型：只看左操作数

MSDN 的移位表把 `<<` / `>>` 当**一元运算作用于左操作数**（VB.NET 还要求右操作数是
`Integer`），所以计数不参与结果类型。改前这里写的是 `promote(左, 右)`，新的混符号
规则会把 `u >> 4`（`u As ULong`）判成 `LongLong`，与发码层投回的 `uint32_t` 两个口径。
现改为只看左操作数（窄整型仍抬到 32 位 —— C3 的 `Integer` 是 16 位而字面量 `1` 一直是
`Long`，不抬的话 `1 << 20` 会被截成 0）。`inferExprType` 的 `Shl/Shr` 分支与
`cgen_expr_binary.cpp` 的 `castBack` 是同一份口径。

## 4. 转换函数 `CSByte / CUInt / CULng / CULngLng`

- 口径与 `CInt/CLng/CByte` 一致：收 `double`，由调用点的 `_Generic`/`NumVal`
  分诊 `BSTR`/`Variant`；沿用 `vb6_OvfChk` 的 **VB6 语义：越界是 Error 6，不是静默截断**
  （`CByte(300)` 那条先例）。`CULngLng` 的上界（2^64-1）装得下 double 的整数域，
  故只挡负数。
- **大小写不敏感**：表键用小写 `csbyte/cuint/culng/culnglng`，与 `cint/clng` 同路，
  所以 `culng(7)` 也能用（探针 `conv_case`）。
- 登记**不加 `calleeParams`** —— 同 `CStr/CInt/CLng/CByte`，让 cgen 的 callee-rewrite
  独立工作（加了会被 Fix 024/029 的实参包装抢先，C2440）。
- 宽度不同的两个邻档一并考虑过：`CShort`（= CInt）、`CUShort`（= CUInt 的 16 位无符号）
  本次未加 —— 用户点名的是那四个。`CUShort` 若要补，照 `CUInt` 抄一遍即可。

## 6. 已知边界（明确记为"不支持/近似"）

1. `f() += 1` 这类**左值有副作用**的复合赋值会求值两次（见 2.1）。
2. `If(True, f(), 0)` 可能同时调用 `f()`（C 无序号化三目，见 2.3）。
3. `VarType()` 对 SByte/UInteger/ULongLong 答**有符号**档（见 2.5）。
4. **64 位整型与有符号型混算 → C3 取 `ULongLong`，VB.NET 是 `Decimal`**（见 3.4 ④）；
   `\`/`Mod` 也一样（VB.NET 的 `\` 表此处是 `Long`、`Mod` 表是 `Decimal`）。
   差异只在"有符号侧为负"或"结果 ≥ 2^64"时可见 —— 那些情形 VB.NET 本身会抛
   OverflowException 或需要 Decimal。要真正对齐得先实现 Decimal 算术
   （`Vb6Type::Decimal` 现在在 `mapType` 里兜底成 `vb6_VARIANT`，RTL 只有 `vb6_CDec`
   装箱，没有任何一条 Decimal 的加/减/乘/除）。
5. **`Boolean` 与 `LongPtr` 不参与 §3.4 的整型提升表**：
   - `Boolean` 走原有的档位兜底（VB.NET 里它参与算术时被强制升 `Short`，C3 保留
     VB6 的老口径；改动它要动 `Byte ⊕ Boolean` 这类既有形状，不在本次范围）；
   - `LongPtr` 的宽度是**目标相关**的而 `TypeSystem` 拿不到目标架构，故依旧不登记
     任何档位（见 3.4 末尾）。后果：`LongPtr + Long` 的结果类型仍是 `Long`；
     x86 上两者同宽、取值不受影响，x64 上这个组合会窄化 —— 属**既有**问题
     （本次之前就是 0 档），要修得先把目标架构贯通到 `TypeSystem`。
6. **`vb6_VariantFromValue` 的 `_Generic` 表里 `unsigned int` / `unsigned long long`
   两档关联的是 `vb6_VariantLong`（int32 形参）** —— 即"无符号值经 Variant 装箱会被
   按 32 位有符号截断"。本次没有正面修它（要连带 VT_UI4/VT_UI8 的全部读取侧），
   而是沿用本特性既定的做法：**把无符号值挡在 Variant 装箱之外**（登记类型 →
   `CStr`/`Debug.Print` 选无符号入口）。§3.4 里那个 `Dim x As LongLong` 的盲区就是
   这条原则的产物（类型看不见 ⇒ 只能走装箱路 ⇒ 撞上有符号兜底）。
   形参/返回槽的 `LongLong` 仍未登记（本次只补了局部与局部 `Const`）。
7. `Eqv`/`Imp` 在无符号档已按位宽收口，但这两个运算符本身极罕见，
   探针未覆盖其 64 位路径。
8. **位运算的"结果类型"与 C 表达式类型可能不一致**：`promote(ULong, Long)` 现在答
   `LongLong`（§3.4 ③），而 `And/Or/Xor` 的发码仍按"任一侧 `ULong` → `uint32_t`"收口。
   值不受影响（掩码结果的最高位不超过 32 位，零扩展即真值），属类型口径的欠账。
9. 类模块**字段**（非局部）为这四档时未进 `knownNarrowIntVars_`（该表随过程入口
   clear，字段应走 symTab）；如遇实际用例再补 `classNarrowIntMembers_`。
