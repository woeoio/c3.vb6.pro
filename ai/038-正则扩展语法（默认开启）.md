# 038 正则引擎扩展语法（默认开启，不设开关）

> 定位：`CreateObject("VBScript.RegExp")` 由内置引擎接管（见 `ai/037`），并在其之上**直接**支持一批
> PCRE2 / Python `re` 的写法。**没有 `Extended` 开关，也不需要打开** —— 引擎默认就认。
> 代价是：凡是真 VBScript.RegExp 报 5017 的这几类写法，本引擎现在按扩展语义工作，见第 4 节「与真组件的分歧」。

## 1. 为什么不做开关

开关的本意是「怕改坏 VB 兼容性」，但它带来三种更坏的东西：

1. **两套语义要各测一遍**：开关关着是一种引擎，打开是另一种，判据要翻倍；
2. **同一段 VB6 代码在两台机器上行为不同**（谁记得设环境变量）；
3. 「先默认关、以后再说」事实上等于永远不开 —— 没人会给旧工程加属性。

所以按用户决定：**默认就是超集**，兼容性风险用「分歧清单」显式记账，而不是藏在一个默认关闭的开关后面。

## 2. 判据分两条线，互不借

| 线 | 脚本 | 基准 | 管什么 |
| --- | --- | --- | --- |
| VB 兼容面 | `tests/regexp_native/run_compare.ps1` | cscript 跑的**真** `VBScript.RegExp` | 真组件支持的语法必须逐字相同 |
| 扩展面 | `tests/regexp_native/run_ext_compare.ps1` | **Python `re`**（`tests/regexp_native/ext_oracle.py`） | 真组件不支持的语法，语义按 PCRE2/Python |

当前读数：

```
PASS regexp_native 用例=50 行 两侧逐字一致（oracle=cscript VBScript.RegExp）
PASS regexp_ext    用例=25 行 两侧逐字一致（oracle=python re）
```

为什么用 Python 3.14 当代理：它 3.11 起有原子组 `(?>...)` 与占有量词 `a++`，3.14 起有 `\z`，
在这几个点上与 PCRE2 同义；`(?P<name>...)` / `(?P=name)` 与 PCRE 的 `(?<name>...)` / `\k<name>` 一一对应。
**Python 表达不出来的地方（PCRE 的 `\Z` = 末尾允许一个换行）在 oracle 里是手工期望，并在源码里注明理由。**

## 3. 支持的扩展语法（全部默认开启）

| 语法 | 例子 | 语义出处 |
| --- | --- | --- |
| 命名组（三种写法等价） | `(?<n>...)` / `(?'n'...)` / `(?P<n>...)` | PCRE2 / Python |
| 命名反向引用 | `\k<n>` / `\k'n'` / `\k{n}` / `(?P=n)` | PCRE2 / Python |
| 串首锚点 | `\A` | 两者一致 |
| 串尾锚点（绝对） | `\z` | 两者一致（Python 3.14 起有 `\z`） |
| 串尾锚点（允许末尾一个换行） | `\Z` | **PCRE2 语义**；Python 的 `\Z` 是绝对末尾，故这条手工给期望 |
| 引号区（字面量） | `\Qa.b\E` | PCRE2 |
| 定长后顾 | `(?<=foo)` / `(?<!foo)` | 两者一致 |
| 原子组 | `(?>a+)` | 两者一致 |
| 占有量词 | `a*+` `a++` `a?+` `a{2,3}+` | 两者一致（实现就是 `(?>X*)`） |
| 内联选项（作用域） | `(?i:...)` `(?m:...)` `(?s:...)` `(?-i:...)` | 两者一致 |
| 内联选项（到组尾） | `(?i)` 作用于本组剩余部分（含后续分支） | PCRE2 行为 |
| 条件组 | `(?(1)yes\|no)` / `(?(<n>)yes\|no)` | **PCRE2 语义**；Python re 无此物，期望手写 |

实现要点（`src/rtl/core/vb6com/vb6com_regexp.c`）：

- **命名组**：名字挂到 `ReProg.gname[组号]`，`\k<name>` 在编译期解析成组号 —— 因此 `SubMatches(i)`
  仍按**左括号出现顺序**编号，与真组件一致，命名只是别名。
- **后顾**：先用 `reFixLen()` 在编译期算出子模式的固定宽度（零宽断言贡献 0、`{n}` 固定、`{n,m}` 变长），
  运行期从 `pos-L` 起跑并用「必须在锚点上收尾」的续延（kind=4）卡住终点。
- **原子组**：用「第一次落点」续延（kind=3）取子模式的**第一次**成功位置，之后不再回退进去。
  占有量词就是 `K_ATOMIC` 套 `K_REP`，没有第二套代码。
- 判「原子组成功与否」不能看 `mRun` 的返回值 —— 中间层会把哨兵 2 归成 1，必须看续延记下的落点。

## 4. 与真组件的分歧（必须知道）

下面这些模式，真 VBScript.RegExp 与现在的本引擎**行为不同**。这是"默认超集"的直接后果，逐一记账：

| 模式 | 真 VBScript.RegExp | 本引擎（默认） |
| --- | --- | --- |
| `(?<x>a)` | `Err 5017`（不认命名组） | 按命名组匹配，`SubMatches(0)` 有值 |
| `\A` | 未知转义 = 字面量 `A` | 串首锚点 |
| `\z` `\Z` | 字面量 `z` / `Z` | 串尾锚点 |
| `\Qa.b\E` | 字面量 `Qa.bE`（`\E` 也是字面量） | 引号区：字面量 `a.b` |
| `a*+` | `a*` 后跟字面量 `+` | 占有量词 |
| `(?>a+)` | `Err 5017` | 原子组 |
| `(?<=x)` | `Err 5017` | 定长后顾 |
| `(?i:abc)` | `Err 5017` | 局部忽略大小写，不影响外层 |
| `(?s:.)` | `Err 5017` | 局部 DotAll，`.` 吃换行 |
| `(?(1)a\|b)` | `Err 5017` | 条件组：组已闭合取 yes，否则取 no |

风险最高的是 `\A` 与 `\Q`：它们**不报错**、只是含义变了。若某个 VB6 工程真拿 `\A` 当字母 A 用，
本引擎会把它当串首锚点 —— 这类模式在真实代码里极少（写 `A` 更省事），但一旦命中就是静默的行为差异。

## 5. 明确不支持的（仍报 5017，不会静默错）

| 不支持的写法 | 原因 / 计划 |
| --- | --- |
| 变长后顾 `(?<=a*)` `(?<=\d+)` | 需要反向扫描或长度上界；PCRE2 有 255 上限，Python 直接禁。本引擎选择报 5017（与 Python 一致） |
| 前向命名引用 `\k<x>(?<x>a)` | Python 也不允许；PCRE 允许。取交集 |
| 内联选项 `(?i:...)` `(?-i:...)` `(?i)` | **已支持**（逐节点冻结旗标，ReCtx 一个字节不改） |
| `\p{L}` Unicode 属性、`\X` 字素簇 | 要 Unicode 表，自己维护不现实；计划接 PCRE2（`#ifdef C3_WITH_PCRE2`），对象模型不变 |
| `\G`、递归 `(?R)`、`(*SKIP)(*FAIL)` 等动词 | 不做；这些是 PCRE 特有、与 VB 生态无关 |

## 6. 夹具与复现

```
tests/regexp_native/
  ReCases.vbs         VB 兼容面基准（cscript 跑真组件）
  ReMain.bas          同用例的 C3 侧；另含 ExtCases()，写 re_c3_ext.txt
  ReApp.vbp           夹具工程（Sub Main，无窗体）
  run_compare.ps1     VB 兼容面对照
  ext_oracle.py       扩展面基准（Python re）
  run_ext_compare.ps1 扩展面对照
  perf_probe.ps1      性能读数（不是门禁；出 6 项 ms 数）
```

复现：

```
powershell -File tests\regexp_native\run_compare.ps1        # 期望 PASS 50 行
powershell -File tests\regexp_native\run_ext_compare.ps1    # 期望 PASS 45 行
powershell -File tests\regexp_native\perf_probe.ps1         # 期望 6 项读数
```

三条都进了 `tests\run_tests.ps1` 的静态段（`[TEXT]` 行），走 `Enter-StaticShard` 分片；
`perf_probe.ps1` **不入 CI 门禁**（性能数字随机器漂，进判据只会造假红）。
环境缺件时脚本自己 `exit 2` → harness 记 SKIP（在汇总行里显形，不当 PASS）。

两条脚本都会**先看编译退出码**再跑 exe。这一条是踩坑后补的：原先只看 exe 是否存在，
编译失败时旧 exe 还在，于是拿旧二进制跑出一堆莫名差异（`(?<x>a)` 明明已移出用例却还在输出里）。

## 7. 下一批（按顺序）

1. `\p{...}` / `\X`：接到 PCRE2，仅在编译期带 `C3_WITH_PCRE2` 时启用，VB 对象模型不动
   （用户 2026-11 决定：这一项**暂缓**）；
2. 性能优化：`Execute` 目前 ~167 µs/次（含 COM 派发），最明显的浪费是每个起点都重建续延链；
   先量 `ReCtx` 复用与 `Execute` 里 `V_ARRAY` 构造谁更贵；
3. 条件组支持 `(?(R)…)`（递归层）、`(?(DEFINE)…)` 这类 PCRE 扩展 —— 判断是否需要；
4. `SubMatches` 在 `Global=True` 下的分配次数（现在每次 `Execute` 都新建集合）。

## 8. 回溯预算：引擎有硬上限（先前文档写错，此处为准）

`vb6com_regexp.c` 里 `#define RE_STEP_LIMIT 2000000`：`mRun()` 每进一个节点计一步，
超过上限就 `return 0` —— **该起点的这次尝试按「不匹配」处理，搜索继续下一个起点**。
`reSearch()` 每换一个起点会把 `steps` 清零，所以 `(a+)+b` 这类灾难模式在长串上不会像
真组件那样一路算下去，而是在每个起点各烧到 2e6 步后放弃。

这是**与真组件的静默差异**：真组件最终会给结果（可能很慢），本引擎可能在 2e6 步处「认输」
并报不匹配。取这个折中的理由：一条正则把 VB6 程序的 UI 线程卡死，比偶尔漏一次匹配更难排查。
要更大空间就调高 `RE_STEP_LIMIT` 重编（不暴露成属性 —— 不想再多一个「谁记得设」的旋钮）。

## 9. 性能实测（2026-11-16，x86，本机）

`perf_probe.ps1` 的原始输出（Timer 步进 ~15.6ms，每项重复到 ≥0.3s 压误差）：

| 项目 | 读数 | 做了什么 |
| --- | --- | --- |
| 200k 字符串、命中在末尾 × 20 | 490 ms | 20 次匹配（每次走完 20 万起点） |
| `\d+` 短串 `Execute` × 20000 | 3349 ms（**167 µs/次**） | 40000 处命中 |
| `^(a+)+b$` 在 24 个 a 上 × 20 | 602 ms（30 ms/次） | 0 命中（在步数上限处认输） |
| 同模式 40 个 a × 5 | 151 ms | 0 命中（长度翻倍但耗时不涨——上限在起作用） |
| `^(a\|aa)+$` 在 26 个 a 上 × 20 | 1.4 ms | 20 次命中 |
| `\d+\s+\w+` 全局找 16k 串 × 20 | 1003 ms | 40000 处命中 |

怎么读这三个数：

- **长串扫描 ~24.5 ms/20万字符**：线性、没有性能悬崖；内层是逐字符 `K_CHAR` 比较 + 起点推进。
- **`Execute` 167 µs/次**偏慢，但这是 `CreateObject` 对象的完整 COM 调用 + 每次新建 `MatchCollection`；
  真实 VB6 用法（一条正则反复 `Execute` 一段文本）里，热点通常在这层而不是匹配本身。
- **灾难模式被上限兜住**：24 个 a 从 0 到 40 个 a，耗时**没有指数上涨**（602ms/20 ≈ 30ms/次 → 151ms/5 ≈ 30ms/次），
  说明 `RE_STEP_LIMIT` 确实在起作用；代价是这两项报「不匹配」而真组件会算出结果。
- `^(a|aa)+$` 在 26 个 a 上只要 1.4ms —— 这条模式其实**有解**（26 是偶数），所以它没烧到上限，
  这也说明「慢」不是普遍现象，只有真无解 + 高分支的组合才会撞上限。
