## 一、结论速览

1. **24 份说明的账**：**21 项已原生复刻**、**2 项降级交付**（Data 走 ODBC、OLE 容器只到本地判据）、**1 项完全缺**（MSHFlexGrid）。UpDown 由 C30-UD 移入“已复刻”；TabStrip 由 **C30-2** 移入；MaskEdBox 由 **C30-3** 移入；MSComm 由 **C30-4** 移入；Adodc / DataGrid 由 **C30-5** 移入（底座 ACE，走它的 ODBC 层）。
2. **默认路已经不再吃 OCX**：凡是 `src/project/frm_parser_util.cpp` 的 `parseControlType` 认得的类型，`controlTypeToWin32Class` 都给出一个 **comctl32 / Win32 / RTL 自注册** 的窗口类，创建走 `CreateWindowEx`，属性与事件由 RTL 表 + cgen 表接管 —— 不 `CoCreateInstance`、不要求注册表。
3. **缺口的真实症状不是"报错"，是 x64 下静默空转**：未识别类型会落到 Fix 143 的真 OCX 宿主（`vb6_OcxHost_Create`），而 32 位 OCX 进不了 x64 进程 ⇒ 控件不渲染、属性读回空、集合枚举为空、退出码照旧 0。**所以补一个控件 = 让默认路少一格 COM**，这是"减少外部 OCX 依赖"的唯一有效口径。
4. **补齐的成本分布很不均匀**：UpDown 已实证"一批能收"（comctl32 现成类 + 一条判据助手，340 行 C，含事件面）；TabStrip（SSTab 已有 768 行实现可裁）同理；MaskEdBox、MSComm 属中等；MSHFlexGrid / DataGrid / Adodc 卡在**数据绑定层**（`DataSource`/`DataField`），不是控件本身的工作量。
5. **业务侧还有第三条路**：VB6 的 `.ctl` 用户控件由 C3 **原生编译**（uc host + 属性包 + 事件），`tests/ucSlider_2022`、`tests/ucTreeView`、`tests/ucSegmentedControl` 三个真例在册。第三方 OCX（Codejock / VBFlexGrid / TeeChart / NewTab）想脱钩，比走编译器内置更现实的是"改成自带源码的用户控件"。

## 二、"算不算内置实现了"的判定规则

一个控件只有**四条证据同时成立**才算完成，缺一条都不算（029 §二-2 那个最贵的教训就是"RTL 写好了、类型表漏一格 ⇒ 什么都没有还不报错"）：

| 证据 | 位置 | 作用 |
|---|---|---|
| ① 类型枚举 | `src/project/frm_parser.hpp` 的 `FrmControlType` | 编译器"认得"这个控件 |
| ② 窗口类映射 | `src/project/frm_parser_util.cpp` `controlTypeToWin32Class` | 创建路真能建出窗口（`nullptr` = 被当"不可见控件"跳过） |
| ③ RTL 实现 | `src/rtl/core/vb6forms/vb6forms_*.c` | 属性 / 方法 / 事件 / 集合对象真的应答 |
| ④ 判据工程 | `tests/ctrl*`、`tests/c29*` | 有真跑断言，不是"编译过就算" |

## 五、已实现项的边界（别把"已出"当"全对"）

1. **视觉样式只有 comctl32 v5**：产物不带 application manifest（029 §八 V2 实测），所以 Toolbar/ListView/StatusBar 是 Win95 观感，`TB_ADDBUTTONSW`/`LVM_*W` 语义正常但主题细节对不上 VB6 装 v6 时的样子。
2. **设计期不执行**：属性页（`.pag`/`.pgx`）、`BeginProperty` 的自定义属性页、右键"自定义"、设计器外观还原一律不做；`.frm` 里的 `BeginProperty` 块按已知口径解析（Font/Images 等），不认识的静默略过。
3. **OLE 拖放不做**：`OLEDragDrop`/`OLEDragOver`/`OLEDragMode` 全族未实现（`tests/pd_oledrop` 只是 PhotoDemon 那侧的探针）。
4. **数据绑定不做**：`DataSource`/`DataField` 不存在，所以 Data 控件只能自己遍历 Recordset，不能绑定到 TextBox/表格。
5. **未识别控件静默回落 OCX（诊断已补）**：`cgen_form_create_controls.inc` 的 Unknown 分支仍走 `vb6_OcxHost_Create`（默认语义没变），但**创建前**会先按 `(类型|控件名)` 去重打一条 stderr 诊断 `C3: note: 控件 … 没有内建原生复刻 …`。口径刻意收窄：**只对 `FrmControlType::Unknown` 触发** —— Menu / WebBrowser / ImageList 这类 `win32Class == nullptr` 但已原生实现的控件不算缺口（实读踩过一次误报，加 `Unknown` 守卫后归零）；诊断不改进出码、不改 stdout，所以存量批处理不会因它变红。
6. **WebBrowser 依赖运行时**：走 WebView2，机上有 Edge WebView2 Runtime 才有浏览器；没有判据工程在册（§三 3.2 表里标"未入册"）。
7. **Data / OLE 不进 CI**：两者判据都只本地跑，门上看不到它们的红绿 —— 改动这两块时别指望 CI 拦住。
8. **合成判据只能证明"我们的写端和读端自洽"**：UpDown（C30-UD-a/b/c）无头判据全绿的情况下，真鼠标一点就露出**四处**，四处都是写端与读端共用同一个错常量/错结构/错时序：
   - **事件号**：`UDN_DELTAPOS` 写成 `-721`，真值是 `-722`（`UDN_FIRST = 0U-721U`，`UDN_DELTAPOS = UDN_FIRST - 1`，SDK `commctrl.h` 逐行核过）；合成助手 `SimDelta` 发的是同一个错号 ⇒ 值照变、buddy 照跟、**事件一条不到**而判据全绿。
   - **加速表结构**：`UDM_SETACCEL` 用了 `ACCEL{fVirt,wKey,wInc}`，真结构是 `UDACCEL{nSec,nInc}` ⇒ `Increment=3` 落成 `nInc=196608`，点一次直接跳到量程端（读数 `A 5→10`、`D 0→20`）。
   - **边界语义**：原生在量程边界**仍发** `UDN_DELTAPOS`（`iDelta` 照原号，值不动）；早期"发即变"⇒ 顶到上限后每次点击多报一条 `Change`（读数 `#8~#11`：值始终 10、`Change` 四条）。
   - **时序**：原生**先发通知、后落值**（`UpClick` 里读到的就是旧值），早期 `SimDelta` 先改后发，把两条时间线抹平了。
   定案口径：`vb6_UpDown_OnNotify` 回 **±1（动了）/±2（点了没动）**；Up/Down 按符号在值变更前发；`Change` 只在 ±1 时**先 `vb6_UpDown_Commit` 落值再发**（处理器读到新值，buddy 文本也已同步），arm 末尾 `return 1` 取消原生那一次实施（不取消会一跳两格）。真手势读数（`tools/updown_manual/UpManual.log`：`#2 UpClick v=5` / `#3 Change v=6 buddy=6`、`#16/#17 UpClick v=10` 无 Change、按住在顶端连出不发 Change）与无头判据 `UE7-chgval=16`/`UE8-upval=10` **双向钉同一件事**。**结论：图形控件的"手势面"至少要有一次真输入读数，合成判据不能替代。**
