# 001-编译优化收益实测报告（opt1~opt4）

> 日期: 2026-09-03
> 对象: vbman 工程（204 个 VB 模块 → 204 个 .c）
> 说明: 本文档记录 4 个编译优化提交的**实测**收益（非估算），含完整过程、数据、结论。

## 背景：近期 4 个编译优化提交

| 提交 | 优化点 | 内容 |
|------|--------|------|
| `665eb4f` | opt1 | cl.exe 编译加 `/MP` 并行标志，加速大型项目编译 |
| `8bdb221` | opt2 | 新增 `--no-warn` 选项，可静默指定 ID 警告（vbman 构建抑制 VB3001/VB3003，926 条警告 → 0） |
| `54c8f70` | opt3 | 增量编译 `--incremental`，基于内容哈希的 obj 级缓存 |
| `8fe7b6c` | opt4 | `--trim-includes` 裁剪未实际引用的跨模块 include，降低 cl 预处理量 |

## 实测环境

- CPU: **2 核**（逻辑处理器 2，物理核 2）—— `/MP` 并行收益上限受此约束
- 编译器: VS2022 BuildTools x64 (`vcvarsall.bat`)，cl.exe
- C3: `\.build\C3.exe` 与 `\.build\C3_nomp.exe`（同批构建 2026-09-02 14:05，仅 `/MP` 开关差异，文件大小一致，A/B 可信）
- 工程: vbman（204 模块），构建命令与生产 `vbman\build_vbman.bat` 一致（`--incremental --no-warn 3001,3003`）
- 工程当前状态: **552 个 cl 错误，构建处于失败态**（影响 opt3 结论，见下文）

## 实测方法与过程

计时采用 PowerShell Stopwatch 包装，包一层 `cmd /c call ...bat`；每次耗时含 vcvarsall 初始化（约 2s 内，可忽略）。基准先跑 2 次验证稳定性（272.8s vs 268.7s，漂移 1.5%）。

### 数据总表（全量构建）

| 配置 | 耗时 | 差异（相对上一行） | 说明 |
|------|------|------|------|
| 无 `/MP` 串行（C3_nomp） | 447.8s | — | 最坏基线 |
| `/MP`（生产 bat 当前参数） | 268.7s | **-179.1s（-40%）** | opt1 生效 |
| `/MP` + `--trim-includes` | 265.2s | -3.5s（-1.3%） | opt4 生效 |
| C3 前端单独（`--emit-c`，不调 cl） | 32.2s | — | 解析+语义+代码生成 |

结论锚点：
- cl 编译阶段 = 全量 - 前端 ≈ **236s，占总耗时 ~88%**
- `/MP` 加速比 **1.67x** = 2 核理想上限（2x）的 **83%**，效率很高

### opt1 `/MP` 实测（最重要收益）

**方法**：同一工程、同一参数，仅切换 `C3.exe`（含 /MP）与 `C3_nomp.exe`（不含），各计时一次全量。

**结果**：447.8s → 268.7s，省 179s（**-40%**）。

**评估**：
- 收益主体来自 cl 编译阶段（~236s 几乎全部可并行）
- 2 核上已达理论上限 83%，**换更多核 CPU 收益近线性放大**——这是 4 项中投入产出比最高的
- 注意 vbman 失败态下 /MP 每次全量仍要 268.7s，此收益固定每次构建都能吃到

### opt2 `--no-warn` 实测

**结果**：926 条 VB3001/3003 警告 → 0；日志体积 137KB → 22 行。

**评估**：
- 时间收益 ≈ 0（警告输出发生在 C3 前端阶段，总 32.2s 内；写 137KB 日志 <50ms）
- **真正价值是日志可读性**：22 行纯错误输出，便于在 2.6MB 错误流中定位 cl 错误
- 属体验优化，非性能优化

### opt3 `--incremental` 实测（关键发现）

**方法**：以生产参数连跑 4 次全量构建，检查 `.c3obj` 增量缓存目录 obj 数量。

**结果**：
- 4 次失败构建后 `.c3obj` 始终 **0 个 obj 文件**
- 对应代码（`msvc_driver.cpp` L626-653）：cl 编译失败（ret≠0）时直接 `return false`，**不写 obj 缓存**

**评估**：
- **当前收益 = 0**：vbman 有 552 个错误 → 每次迭代必然全量 268.7s，增量缓存完全没建立
- **成功路径下的潜在收益**（预计）：改 1 个 `.bas` 的迭代 = 前端 32s + 只重编 1 文件 ≈ 33s vs 268.7s → **省 ~88%**
- 解锁条件是先把 552 个错误清零（opt3 是"未解锁的期权"）

### opt4 `--trim-includes` 实测

**方法**：生产参数 ± `--trim-includes` 各跑一次全量。

**结果**：268.7s → 265.2s，省 3.5s（**-1.3%**）。

**评估**：
- include 裁剪量很大（跨模块 include 行 733 → 162，-78%），但时间收益微小
- 原因：2 核下 cl 瓶颈是 CPU 编译本身，预处理 I/O 不是瓶颈
- 附带收益：诊断输出更小、cl 内存占用略降
- 注意：生产 `build_vbman.bat` **尚未启用 `--trim-includes`**（代码已支持，参数未加），要兑现这 1.3% 需先加上

> **后续（2026-11-12，账 §56.52）**：`--trim-includes` 这个 flag **已撤掉**，include 瘦身
> 改成编译器的**固定行为**（用户裁定「副作用选项没啥好处」）。原先 opt4 的判据（driver 用 AST
> 扫描收集引用）**残缺** —— AST 遍历走不到 `VariableDecl`/`ParameterDecl`/`TypeDecl`/`TypeMember`
> 里的类型引用位点 ⇒ 那份名单会漏头 ⇒ 编译断。新的判据只有一处权威 = **发码器在发出外部
> 引用那一刻登记**（`usedExternalModules_`），外加「文本 token × 符号表」两路兜底。
>
> 本节那 1.3% 的收益结论**已过时**：那是在 2 核小工程上测的，而 PD 那种 539 模块的量级上
> 重复预处理才是主成本（6.5 GB 头文本 / 29 万次头文件打开）。新收益见 §56.52。

## 附：opt3 "失败也写 obj" 可行性调研

结论：**可行，收益明确**。三条实证链：

1. **MSVC 行为验证**（微型实验，good.c + bad.c 一起 `/MP` 编译）：
   ```
   CL_RC=2 → good.obj 已生成并保留，bad.obj 完全不存在
   ```
   即失败批次中，成功文件 obj 在、失败文件无 obj。用"obj 是否存在"即可精确区分，不会误缓存坏 obj。

2. **错误分布**：552 个 `error C` 集中在 **63/204 个文件**（Demo.c 78、cZipArchive.c 53、ToolsTlsThunks.c 51…），意味着 **141 个文件（69%）实际编译成功**，其 obj 每次都被白白丢弃。

3. **缓存命中逻辑自带双保险**：record（源哈希+deps+opts）与编译成败无关；即使 record 误写，下次命中校验还要求 obj 真实存在，失败文件无 obj 自然不命中。

**失败也写 obj 后的预估收益**：

| 场景 | 耗时 | 说明 |
|------|------|------|
| 现状（失败即全量） | 268.7s | 前端 32s + cl 204 文件 236s |
| 失败也写 obj 后首轮迭代 | ~105s（-60%） | 前端 32s + 只重编 63 个错误文件 |
| 修复过程中 | 持续收敛 | 每修好一批，下批重编数减少，直到 0 |

**实现要点**（改动很小）：在 `compileAndLinkIncremental` 失败分支（cl ret≠0、写错误日志之后、`return false` 之前），复用成功路径的 obj 收割循环——只缓存本次实际成功（obj 存在且大小>0）的文件，失败文件从 cacheData 移除记录，照常写 cache.txt，仍返回编译失败。

**顺带发现的风险点**：现有缓存 record 的 optsFp 不含 **cl 版本**——若将来升级 VS/cl，旧 obj 可能被误命中。建议届时把 cl 版本指纹纳入 optsFp。

## 汇总结论

| 优化 | 当前兑现收益 | 潜在收益 | 备注 |
|------|-------------|---------|------|
| opt1 `/MP` | **-40%**（179s/次） | 随核数放大 | 唯一已稳定兑现 |
| opt2 `--no-warn` | ~0 | 日志可读性 | 体验优化 |
| opt3 增量 | 0（失败态未解锁） | 通过后 -88%（268.7→~33s/次迭代） | 需先修 552 错误 |
| opt4 trim | -1.3%（3.5s/次） | 受限 | bat 尚未启用 |

**当前最大瓶颈不是编译速度，而是 552 个编译错误本身**——它让每次迭代固定付出 268.7s 且锁死 opt3。优先级建议：
1. 修复 552 错误（解锁 opt3 的 -88%，opt4 也随之自然进 bat）
2. 实现"失败也写 obj"（修复过程中每轮迭代再省 ~160s）
3. 硬件升级时 `/MP` 收益翻倍、增量模式收益放大
